# 改用 1.001.104（2024-10-15）當移植來源

2026-11-28 的比對結果。1.001.104 是最後一個還能玩默里迪亞任務的版本，從這版起移植資料全部改用它。2024-06 只拿來對照。

## 印模產生設定（9ba626 / b8fd4d2cede20ed7 / 8105986402e7f076）

- 版本 7，S0 有 141,783 筆，**每筆 0x38**（2024-06 是 0x34，現行版 0x44）。最後 4 個位元組在整個 S0 都是 0。
  S1～S5 的單筆大小三個版本都一樣：0x40、0x38、0x10、8、8。用 0x38 解析，剛好結束在 0x9cd33c。
  codex 另外窮舉所有能讓五個區段對上的大小，也只有 0x38。
- 轉成現行版：取前 0x34 位元組，後面補 16 個 0。
- **+0x2C：一律 +2。** 960 個兩版共有、筆數相同的印模（42,917 筆）都符合，偶有例外是內容本身改了。
  2024 版那張表的「6→11」其實是 2024 之後改了內容（2024 的 6 在 1.001.104 有一部分是 9），不是編號換算。
  改用 1.001.104 之後，那 6 筆紀錄是 6→8，codex 也用 ID 512 直接對照確認。
- **目標類型：22～28 一律 +1。** 關閉 Termicide 25→26、突變蟲卵 26→27、部署暗流體 27→28、投放點 28→29。
- +0x06、+0x07 是沒初始化的填充位元組（內容像 ASCII 的 tab、空格），每版都不同，可以忽略。
- **+0x10 是印模自己關卡檔裡的物件索引**，不是 S5 索引。所以設定補丁和資源包一定要出自同一版本：
  1.001.104 的設定配 1.001.104 的關卡。
- `port_lgs.py` 會依 S0 紀錄大小自動判斷來源版本（0x34 = 2024-06，0x38 = 1.001.104），各用各的換算表。
  輸出在 `darkfluid/generated/darkfluid-settings-1001104/`。

## 現行版還留著暗流體點 1、2 的設定

現行版的 S1 有兩筆孤兒設定：`0x494D4CF25E7E4384`（對應暗流體點 1）、`0x23D76A72526FCF1C`（對應暗流體點 2）。
目標類型是 [29, 28]，S0 分別有 627 筆和 370 筆，比 1.001.104 的 587 筆和 350 筆多；舊紀錄的 ID 全都在裡面。

但現行版沒有這兩個 key 的關卡檔，也沒有登記擺放位置，所以不能直接拿來用。
1.001.104 的關卡在 `fb04c61383402693` 和 `8ac0fe970e89087f` 資源包裡，key 就是關卡檔的名稱。

S5 的最後 6 個名稱在新舊兩版都不是資源，在解密後的設定檔裡也找不到，大概是印模內部的參照。
兩版的情況相同，所以不影響移植。

## 印模形狀（generated_stamp_settings）

這個檔案是單一 LDLD 實例，資料從 0x18 開始。每筆是印模 key 加 0xD8 位元組，碰撞圓每個 20 位元組（x、y、r，後面接壓平欄位）。

- 暗流體 8 個印模和 TCS-A、TCS records-only 這兩個，在 2024 和 1.001.104 之間除了檔案內位移以外**完全相同**。
  mod 裡 kC0～kC10 的圓形數值不用改。
- TCS-B（e3319）在 1.001.104 多了子關卡清單（+0x68 關卡 0x76b4…、3 筆），+0xD0 是 1。之後移植 TCS 時要一起處理。

## 單位轉換器對 1.001.104 的結果（test_convert_unit_v5.py）

測試對象是 GPU 資料兩版相同的 196 個單位：89 個完全一致，79 個大小不同，28 個大小相同但內容有差。

- **大小不同的主因是 CustomizationInfo**（71 筆）：現行版給部分單位加了一個屬性 hash `0x328f2050`。
  型別 2、長 4、浮點值 0.3、0 或 0.7，由美術逐一設定。現行版也有 180 個單位沒有這個區段，所以缺它不影響載入。
- TransformInfo（10 筆）、MeshInfo、LightList 的差異是重新匯出的內容。
- 結論：轉換器的格式部分沒有問題，剩下的差異是內容。
