# 部署暗流體的執行邏輯（game.dll 25480438，2026-11-28 反組譯）

舊版的流程完全靠行為（behaviour）推進。這些行為的程式碼在現行版還在，三張分派表都有它們專屬的處理程式。

## 行為 id

讀自現行版解密後的 `generated_entities.dl_bin` 裡的 BehaviorComponentData。
每筆紀錄 12 位元組 `{BehaviorId, f32 task_cooldown, TaskUser}`，索引表的每筆是 `{u64 實體, u32 紀錄}`。

| id | 名稱 | 實體 |
|---|---|---|
| 388 | objective_bug_tcs_03_backpack | 部署暗流體 `ba58a7667aa11627` |
| 389 | objective_bug_tcs_03_bridge | 印模裡的 bridge（推測是 `f62ebb07`） |
| 390 | objective_bug_tcs_03_thumper | 投放點 `0f19b7b633e9aa3c` |

社群 enum（shalzuth）只有 472 個，其中 240/241/242 是同一組，編號跟現行版的 693 個不同。

三張分派表都用 `id - 1` 查 693 格的 32 位元偏移：

| 表 | 位址 | 預設處理 | 388 | 390 |
|---|---|---|---|---|
| Update | 0x4795C4 | 0x479592 | 0x476B60 → 0x36D390 | 0x476B6A |
| Stage | 0x493108 | 0x48EEF6 | 0x491096 → 0x36D1E0 | 0x4910AB → 0x36E190 |
| Event | 0x4A0154 | 0x4A0139 | 0x49B67D（0x36D060 同一份邏輯） | 0x49B81E → 0x36DA50 |

## 目標狀態

| 位置 | 內容 |
|---|---|
| ObjectiveManager（`*(game+0x3326DA0)`）+0x24 | 目標數 |
| +0x50 | 實體資訊指標，`+0` 實體 hash、`+8` 目標 id |
| +0x60 | 目標陣列，每筆 0x1078 |
| +0x68 | 同步紀錄，每筆 0x64 |
| +0x38 | id → 索引的雜湊表 |

- 狀態值在目標陣列的 +0x1018，從同步紀錄的 +0x20 複製過來。
  - **0 = 啟用，1 = 尚未啟用（start_inactive），2、3 = 已結束。**
- `0x4D7FC0(_, id)` → `0x5D80F0`：啟用（1 → 0）。`0x4D8030`：停用（0 → 1）。
  `0x5D8AD0(mgr, id)` 檢查「狀態不是 2 也不是 3」，也就是目標還沒結束。
- `0x4D7C00(&out, ctx)`：找出行為所屬實體的目標 id。
- `0x4D7D30(id, stage)`：把同步紀錄的 +0x18 設成 stage，+0x24 歸零，再交給 `0x5D54D0`。
- `0x4D7EA0(id)` → `0x5D7E40`。`0x5D7CE0(mgr, id)` 最後也呼叫 `0x5D7E40`。推測是推進或完成目前的步驟。

## 流程

1. **部署（388）收到事件 `0x8ED59ACA`**：推進自己的目標（`0x5D7CE0`），並發出事件 `0x0F197F6D`（`0x1762900`）。
2. **投放點（390）收到 `0x0F197F6D`**：讀自己單位的腳本資料 `0xF52812AA`（`0x4CDBA0` → `0x17627B0`，經過 EngineApi+0xB8）。
   值是 `id_01`、`id_02` 或 `id_03` 時，就用 `0x4D7FC0` 啟用自己的目標。
   - hash 是 murmur64a 的高 32 位元：`id_01` = 0x32509C88、`id_02` = 0x5FB6062C、`id_03` = 0x7A7A7F79。
   - 1.001.104 的暗流體點 1、2 關卡各有 3 筆這種腳本資料，跟在 3 個 `bug_fog_generator_tcs` 擺放單位後面。轉換後的資源包也保留了全部 6 筆。
3. **投放點的各階段**：
   - 第 1 階段：等目標還沒結束（`0x4D8440` → `0x5D8AD0`），然後進第 2 階段。
   - 第 2～8 階段（`0x36E190`，跳躍表 0x36E430）：各發出一個事件（`0xB8EE5B6B`、`0xB0CF85E1`、`0x311E1A6E`、`0xDF42086C`、`0x6FEC3362`、`0x8EFF1CFE`）。
     第 3 階段用 `0x4D7D30(id, 1)` 把目標推到第 2 步（防守）。第 8 階段呼叫 `0x5D82D0`。
   - 收到事件 `completed`（0x2504C72E）時進第 2 階段，收到 `0x78D8E978` 時進第 3 階段。
4. **部署完成**：部署的第 1 階段看自己的進度值 +0x1A0。到 1.0、2.0 時各發一個事件（0x394F0478、0x1A2D3BB4），到 3.0 時完成目標，進第 2 階段。
   也就是 3 個投放點都完成，部署才算完成。
5. 事件由引擎的事件派送送進 `BehaviourEvent`，呼叫者是 0x843040、0x843930、0x843CF0。
6. **`0x8ED59ACA` 的來源**：程式裡沒有任何行為直接發出它。真正的發送者是 `0x5DB6E0(mgr, 新單位, 舊單位)`，由 `0xB5A6D0` 呼叫。
   它會走過每個目標，實體目前的單位（+0xC）如果是舊單位，就用 `0xFDD750` 把 `0x8ED59ACA` 發給那個目標實體，並登記「舊 → 新」的單位對應。
   也就是**目標的單位被換成另一個單位時**發出的事件。`0xB5A6D0` 本身也會發同一個事件。
   - 推測：背包 `0732`（行為 435）和鑽頭投放 `b127`（行為 552）都有 ObjectiveDynamicLink。暗流體容器降落後動態連結到部署目標，部署因此收到 `0x8ED59ACA`。
   - 其他實體的行為 id：鑽頭投放 `b127` = 552，背包 `0732` = 435，容器 `0e4e` 沒有行為。

## 完整流程（行為邏輯加上使用者描述的舊版玩法）

1. **部署暗流體**：任務開始就啟用。在部署標記 150 m 內呼叫暗流體容器（戰備 29，最多 12 次）。
2. **容器降落**，以動態連結接上部署目標，引擎發出 `0x8ED59ACA`（推測）。部署推進到「Transport Vessel to Payload Site」，並發出 `0x0F197F6D`，3 個投放點（`id_01～03`）一起啟用。
3. **每個投放點**（使用者描述）：到現場 → 12 m 內呼叫地殼鑽頭（戰備 64，投放點第 1 步）→ 鑽頭投放 → 放入容器（鑽頭投放 `b127` 的 ObjectiveCarryDelivery 需要容器 `0e4e`）→ 刷怪防守（MinigameWait，投放點第 2 步「Defend Drill」）→ 鑽頭跑完，投放點完成。
4. **部署進度**：每完成一個投放點，部署進度 +1；到 3.0 時部署完成，接著撤離。
5. **1.0.4 的影響**：所有目標一開始就啟用，所以第 2 步的「容器降落 → 開放投放點」不再是必要條件。

## 1.0.4 的做法

- **全程開放**：每 2 秒檢查一次，部署或投放點的目標只要狀態是 1，就用遊戲自己的 `0x4D7FC0` 啟用，等同收到 `0x0F197F6D`。每個目標最多試 3 次。
  - 1.0.3 改 ObjectiveComponent 那條路從來沒生效：`component_record` 對 0f19 回傳 0。
- **9 級防護**：改掛在 `0x5D22B0`，見原始碼的說明。
